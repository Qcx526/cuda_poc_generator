# P4-W 换目标：哪些方法带走，哪些结论留下

报告语言：`zh-CN`。结论：**换 CVE 可以，方法全部保留**，但要先分清两类资产。

## 1. 可以带走的（目标无关，已在代码里）

| 资产 | 位置 | 为什么通用 |
|---|---|---|
| 模糊测试引擎 | `src/fuzz_core.py` | 只认 Candidate/Outcome/分桶/语料，grammar 与 runner 注入 |
| 追踪层 | `src/trace_core.py` | 只认 Probe/TraceResult/Provider，换调试器或目标只写适配器 |
| 到达判据 | `tools/driver/probe_runner.py` | 先执行判接受，再对通过的用例下探针 |
| 故障归因 | `tools/driver/sm3.py::fault_frame` | 崩溃必须落到目标模块才算证据 |
| 规格与写回 | `src/spec_model.py` + `record_history` | 执行级事实进提示词，规格随运行进化 |
| 可执行 harness 范式 | `tools/driver/shader_runner.cpp` | "把 COM/系统调用固化进 C，Python 只产输入"这个模式可复制 |

## 2. 方法层面真正沉淀的四条经验

1. **崩溃先归因**：47 个崩溃全是 d3d9 校验器的，不是驱动的。没有模块归因就会误报。
2. **偏移要看清相对谁**：`symbol+0x…` 是相对符号，不是模块；按错的地址下断，
   "没有命中"本身就不可信。地址要用**机器码搜索**交叉验证。
3. **判据要防回显**：用"输出含某字符串"判定命中，会匹配到调试器回显命令的那一行。
   必须匹配 `Breakpoint N hit`。
4. **观测点要对**：程序在运行时会被拷贝，盯调用方缓冲区永远看不到解码器。

这四条与具体 CVE 无关，换任何驱动目标都成立。

## 3. 只属于 0107 的（不带走）

- 地址：0x12A3560（越界助手）、0x1503177（调用点）、0x15030FA（分派块）
- 条件：opcode 0x7D、寄存器类别 1、低 24 位 < 3
- 结论：合法 SM3 指令到不了该分派块
- 输入形态：SM2/SM3 着色器、D3D9 设备路径

## 4. 换目标时必须先回答的问题

选新 CVE 前，用这四条筛：

| 问题 | 为什么 |
|---|---|
| 入口是否**用户态可达**？ | 内核态一崩就是蓝屏，本机不能裸跑 |
| 触发是否**确定性**？ | 竞态类（如 CWE-367）成功率极低，不适合做首个成功样本 |
| 输入媒介是否可构造？ | 文件/API 参数好办；需要特定硬件状态就难 |
| 是否有**可观测判据**？ | 崩溃、返回值、模块归属，至少有一个 |

## 5. 候选评估

| 候选 | 入口 | 风险 | 判断 |
|---|---|---|---|
| CVE-2024-0107 | 用户态 D3D9 → nvgpucomp64 | 无蓝屏 | 已做，卡在"畸形但过校验" |
| CVE-2024-0090 | 显示驱动，输入里出现 `nvlddmkm` | **蓝屏** | 内核驱动，需先有 VM 快照 |
| CVE-2024-0091 | 驱动 API 把不可信值当指针；输入只提 `nvapi64.dll / nvcuda.dll / nvml.dll` | **低（用户态）** | **首选**：NVAPI 是用户态入口，崩在用户态 DLL 不会蓝屏 |
| CVE-2026-24191 | 显示驱动 TOCTOU | 蓝屏 + 竞态 | 最不适合做首个样本 |
| CVE-2025-33231 | Nsight（用户态工具，DLL 搜索路径） | 无蓝屏 | 非内存破坏类，但**最容易拿到第一个成功样本** |

## 6. 建议路径

1. **先立一个无风险的成功样本**（33231 或同类用户态目标），证明"规格 → 生成 → 执行 → 归因 → 报告"这条链在新的目标类别上也成立；
2. **同时准备 VM**（Hyper-V + 快照），为内核类目标解锁；
3. 0107 保留为"深度案例"：它的失败原因（需要畸形但过校验的字节）本身就是有价值的分析结论。

**核心判断**：换 CVE 不损失任何工程投入——引擎、追踪层、归因、判据、写回都可以直接复用，
只需要为新目标写一个 grammar + 一个 runner。


## 7. 0091 的实际进展与判断（2026-10-23 追加）

| 步骤 | 结果 |
|---|---|
| 驱动版本门 | ✅ 551.61 ∈ [550, 552.55)，本机受影响（原输入写 617.42 是错的） |
| NVAPI 基线 | ✅ `nvapi_QueryInterface` + `Initialize` 返回 0 |
| 接口面枚举 | ✅ 静态读出 **2166 个 id**（16 字节/项的表） |
| 函数名 | ✅ 492 个（NVIDIA 开源 `nvapi_interface.h`） |
| 函数原型 | ✅ 487 个，其中 **423 个带指针参数** |
| 基线调用（60 个无句柄候选） | ⚠️ 1 个 OK、38 个错误码、**12 个崩溃** |

**那 12 个崩溃不能算漏洞。** 把任意指针传给一个期望 `ID3D11Device*` 的函数，
它当然会崩——这是调用方违约，不是 CWE-822。要区分"驱动没校验"与"我传错了对象"，
必须先知道每个参数是**对象句柄**还是**数据缓冲**，而公告没给。

**结论**：0091 在缺少函数名的情况下不可判定。它的公开资料只有一句
"a user can cause an untrusted pointer dereference by executing a driver API"，
没有报告、没有 PoC、没有函数名。
