# 归因：把"崩溃点"变成"可以写进论文的结论"

一个崩溃点本身不是结论。它必须回答：**这是哪条 CVE，还是没人报过的东西？**

## 一、为什么必须机械地做

手工比对有两个失效方式：

1. **把已披露的当成新的** —— 报上去被打回，浪费一轮沟通
2. **把新的当成已披露的** —— 直接放弃，成果消失

两者都源于"凭印象匹配"。所以这件事由代码做，且代码必须**宁可说不知道**。

## 二、输入

| 来源 | 内容 |
|---|---|
| `data/mutation/sites.json` | 崩溃点 + 在哪些版本崩/不崩 + 触发配方 |
| `data/cve_catalog.json` | 23 条 CVE 的组件、CWE、受影响范围、修复版本、证据来源 |

目录的 `fixed_evidence` 字段区分来源：公告（`a_id/5661`）、NVD 区间、
还是**本仓库实测**（`CVE-2024-53877`：12.4 崩、13.0 不崩）。

## 三、判定规则

```
组件匹配？
  否 → 无对应公告（候选新发现）
  是 → 修复版本与"我们观察到的不崩版本"一致？
          唯一 → 已披露 CVE-XXXX
          多个 → 同组件，无法唯一确定（列出全部候选）
          零个 → 已修复但无对应公告
```

**关键：多候选时不投票、不猜。** 报出全部候选，让人去查补丁差异。

## 四、当前结果

| 崩溃点 | 判定 | 崩在 | 不崩在 |
|---|---|---|---|
| `cuobjdump+0x66000` | 无法唯一确定（3 个候选） | 12.4 | 13.0 |
| `cuobjdump+0x67000` | 同上 | 12.4 | 13.0 |
| `cuobjdump+0x68000` | 同上 | 12.4 | 13.0 |
| `libc.so.6+0x183000` | 无对应公告 | 11.2 | — |
| `libc.so.6+0xa5000` | 无对应公告 | 12.4 | 13.0 |

三个 cuobjdump 点匹配到 `23247 / 23339 / 23346`——同一批公告、同一修复版本，
**光靠版本区分不了**。

## 五、怎么才能唯一确定

需要**访问类型（读/写）**，它直接对应 CWE：

| 访问类型 | CWE | 候选 |
|---|---|---|
| 越界读 / 空指针读 | CWE-125 / CWE-476 | 23247、23346 |
| 写坏内存 | CWE-121 / CWE-787 | **23339**（栈缓冲区溢出，写） |

我们这三个点在 12.4 上测到的是 `null-read` / `read-out-of-bounds`，
**这本身就能排除 23339**（它写）。

差一步：台账目前没存访问类型。加上之后，候选会从 3 个缩到 2 个甚至 1 个。

## 六、两个必须承认的局限

1. **目录不全**：23 条里只有 7 条有修复版本。没有修复版本的公告无法参与匹配
   （`CVE-XXXX` 那条测试就是守这个）
2. **libc 点无法归因**：故障指令在 libc 里，不在目标程序里。这类点永远匹配不到
   任何 NVIDIA 公告——应当单独标为"归因弱"，而不是"新发现"

## 七、用法

```bash
python -m src.attribute          # 只看不改
python -m src.attribute --write  # 把判定写回台账
python -m src.attribute --site cuobjdump+0x68000 --show
```
