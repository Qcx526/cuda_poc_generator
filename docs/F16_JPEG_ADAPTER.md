# F16：JPEG 输入适配器与 A/B 真实对照

起点 `6bc8bba`。本轮把"从零手写字节"换成"计划 + 适配器构造"，并用同一套探针做对照。

## 一、先修正 F15 的两处归因

### 1.1 第七轮不是"没有 Huffman 数据"

审计说得对。段结构显示三个文件都含 `APP0 DQT SOF0 DHT(len=210) SOS`——DHT 和 SOS 都在，
模型确实写了 Huffman 表与 scan 构造。用独立解码器（Pillow/libjpeg）复核：

```
benign_64x64_baseline.jpg      OSError: broken data stream when reading image file
ctrl_dri64_64x64.jpg           OSError: broken data stream when reading image file
poc_dri0_64x64.jpg             OSError: broken data stream when reading image file
```

所以失败层是**熵编码比特流非法**，不是标识符缺失。nvJPEG 在 STAGE6 返回 BAD_JPEG，与独立解码器一致。
`docs/F15_R3_PROBE_AND_HARD_NEGATIVE.md` 已按此更正。

### 1.2 校验和差异补上了可复现原始记录

`data/driver/f15/checksum_records.json`：每版本重复 3 次，逐条记录 DLL 路径与 SHA256、
输入 SHA256、探针 SHA256、完整 stdout。

| 版本 | 校验和（3/3） |
|---|---|
| 11.4.0 | `1356454264` |
| 12.3.1 | `1356454264` |
| 13.2.2 | `1160047537` |

输入 `bc7b35044512b1a9…`、探针 `dbd52b276ee71e76…` 三次相同。差异可复现，但**仍不构成"已修复"的证据**。

## 二、JPEG 适配器（`src/jpeg_adapter.py`）

| 能力 | 实现 |
|---|---|
| 合法基线 | Pillow 真实编码（非手拼），可选灰度/RGB、尺寸、质量 |
| 受控变异 | `set_sof_size` / `set_component_sampling` / `set_dri` / `insert_segment` / `strip_segment` |
| 恢复对照 | 按同一计划把被改字段写回原值，其余字节不变 |
| 双路校验 | 段遍历器（结构）+ Pillow 解码（参考解码器） |
| 证据 | 基线/变异/对照三份文件 + 各自 SHA256 + 变异说明 `plan.json` |

**不变量**：适配器不重算熵流。改几何字段会让参考解码器拒绝——这本身是被记录的合法结果，
不是"构造失败"。模型只出计划，不再碰二进制。

## 三、A/B 对照（同一探针、同一版本、同一判据）

### 3.1 A 臂：从零手写（F15 第 1–7 轮归档）

| 指标 | 值 |
|---|---|
| 文件数 | 18 |
| 参考解码器接受 | **12/18 = 67%**（6 个 OSError） |
| nvJPEG 执行次数 | 45（9 文件×3 版本 + 9 文件×2 版本） |
| STAGE4 通过 | 36/45 = 80% |
| 完整解码（STAGE7） | 30/45 = 67% |
| 可信异常 | 0 |

### 3.2 B 臂：计划 + 适配器（本轮新跑 3 轮）

| 指标 | 值 |
|---|---|
| 文件数 | 9（3 轮 × 3 件） |
| 参考解码器接受 | **9/9 = 100%** |
| nvJPEG 执行次数 | 18（9 文件 × 2 版本） |
| STAGE4 通过 | 18/18 = 100% |
| 完整解码（STAGE7） | 18/18 = 100% |
| 可信异常 | 0 |
| 候选/对照配对 | 3/3 轮齐备 |

### 3.3 结论

**输入有效性：67% → 100%；完整解码率：67% → 100%。**
这是本轮唯一可宣称的提升，且是"输入生成能力"而非"CVE 复现率"——异常数仍是 0。

## 四、模型提出的计划（全部留档）

| 轮 | 假设 | 操作 | 结果 |
|---|---|---|---|
| 1 | DRI=0 让 restart 分组取模除零 | `set_dri 0` | 三件全部正常解码 |
| 2 | 同上（重复） | `set_dri 0` | 同上 |
| 3 | DRI=0，并显式插入 `FFDD 0000` | `set_dri 0` + `insert_segment DD` | 同上 |

**问题暴露**：三轮几乎同一个计划，没有多样性。适配器让"计划能落地"，但**没有让模型产生不同的假设**。

对照 A 臂：A 臂至少换过三类（零值字段 / 派生量 / DRI），B 臂反而收敛到同一个。
这说明**格式感知提高了构造成功率，但没有提高假设多样性**——两者要分开评价。

## 五、反馈闭环

B 臂每轮都把以下信息回灌：三个文件各自的参考解码结论、段结构、poc 在 13.2.2 上的 STAGE4 结果与最后阶段。
第 3 轮的"显式插入 FFDD 段"正是对第 2 轮"担心 interval=0 被当成删除"的回应——**这是真实反馈驱动的修正**，
但修正的是构造细节，不是假设本身。

## 六、可迁移性

| 能力 | 是否可迁移 | 说明 |
|---|---|---|
| "计划 + 适配器"分层 | 是 | ELF/cubin 已部分具备（mutation 算子），JPEG 把它落到具体格式 |
| 双路校验（结构 + 参考消费方） | 是 | ELF 用 readelf/objdump 即对应"参考解码器" |
| 恢复对照按同计划生成 | 是 | 与格式无关 |
| 变异不变量（不重算派生数据） | 需按格式定义 | JPEG 的熵流对应 ELF 的段内容 |
| IOCTL 后端 | 未实现 | 需要设备身份、控制码、缓冲区布局、权限；本轮不建空壳 |

## 七、未解决问题

1. **假设多样性**没有改善；B 臂三轮同质。若要提升，需要在提示里显式要求"与上一轮假设的类别不同"，
   并对计划做类别去重检查；
2. 异常仍为 0，`NOT_VERIFIED` 不变；
3. 适配器目前只支持 5 种操作，`SOS` 参数与 progressive 未覆盖；
4. 未证明真实越界写（需要 PageHeap/ASan）。
