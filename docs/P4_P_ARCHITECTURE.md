# P4-P 架构改造：让"任何类型"成立，并把复现率从 1/3 提上去

报告语言：`zh-CN`。回答两个问题：为什么现在只能做一类漏洞；怎么改。

## 1. 现在的结构性问题：三件事被绑死了

```
输入模型（EVS）──写死──> 生成提示词
执行方式 ──写死──> Linux 容器 + bash 矩阵
评级 ──写死──> 退出码/信号
```

三处写死带来三个后果：

| 后果 | 证据 |
|---|---|
| 驱动类永远跑不起来 | 目标在 Windows，执行在 Linux 容器（`nvcuda.dll` 加载即失败） |
| 只能处理"文件作输入"的漏洞 | `input` 概念默认是文件；API 序列 / IOCTL / 报文无法表达 |
| 只能处理"崩溃型"漏洞 | 评级只认 exit code，静默越界读、逻辑错误无法判定 |

这三点不是难度问题，是**表达能力问题**。

## 2. 目标架构：五个可替换层

```text
┌──────────────────────────────────────────────────────────────┐
│ 1 Spec (EVS v2)                                              │
│   identity / anchor / parser / observable / oracle / history  │
│   + target_profile{platform, privilege, medium, device}       │
└───────────────┬──────────────────────────────────────────────┘
                │ 声明"这个目标需要什么"
┌───────────────▼──────────────────────────────────────────────┐
│ 2 Backend registry（能力选择，不猜）                          │
│   container(Linux,user,file)                                  │
│   windows_native(Windows,user,api_sequence)  ← 本期新增        │
│   vm_snapshot(any,kernel)                    ← 待建            │
│   remote_device(甲方硬件/开发板)              ← 待建            │
└───────────────┬──────────────────────────────────────────────┘
                │ 统一返回
┌───────────────▼──────────────────────────────────────────────┐
│ 3 ExecutionObservation（后端无关）                            │
│   exit_code / fault_module / reached / stdout / artifacts     │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│ 4 Grader（按 observable 类型分派）                            │
│   signal | exit_code | asan | valgrind | wer | output_diff    │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│ 5 Controller（策略层）                                        │
│   差分判定 → 失败分类 → 反馈/写回 → best-of-n → 升级探测       │
└──────────────────────────────────────────────────────────────┘
```

**核心变化**：把"怎么做"从代码里搬到规格和注册表里。新增一类目标，只需要
加一个后端 + 一份规格，不动评级与控制器。

## 3. 能力矩阵：哪类漏洞需要什么

| 漏洞类型 | 输入媒介 | 需要的后端 | 所需权限 | 可观测信号 |
|---|---|---|---|---|
| 工具链文件解析（0110/23339） | 文件 | container | 用户 | 退出码/信号 |
| 用户态驱动（0107 nvgpucomp64） | API 序列 + 着色器字节码 | windows_native + GPU | 用户 | 进程崩溃 + 故障模块 |
| 内核驱动（2026-24191） | IOCTL | vm_snapshot | 内核 | bugcheck / WER / minidump |
| 库类（nvJPEG / CV-CUDA） | API 调用 | container 或 native | 用户 | 信号 / ASAN |
| 服务类（Triton） | 报文 | container + 网络 | 用户 | 响应差异 |

后两种今天就能加：`container` 后端已经支持，只缺规格里的 `invocation` 与 `observable`。

## 4. "任何类型"如何成立（以及它的边界）

成立的条件是**三件事都能被规格表达**：输入媒介、执行位置、判定信号。
EVS v2 已具备前两项（`medium` / `target_profile`），第三项通过 `observable` 的
枚举扩展（signal / exit_code / asan / valgrind / wer / output_diff）。

**明确不覆盖**：没有可观测差异的逻辑漏洞（如"少校验一个字段但结果仍正确"）。
这类需要**语义 oracle**（输出对比、副作用检查），属于下一阶段，不建议现在硬塞。

## 5. 复现率：四个乘数，而不是一个技巧

设单候选成功率为 p，则 n 次独立尝试的成功率为 `1-(1-p)^n`。

| 机制 | 作用 | 现状 |
|---|---|---|
| 规格锚点（consumed_fields / baseline / observed crash） | 抬高 p | 已有，0076 靠它从 0 → 成功 |
| 类型化反馈 + 变异点写回 | 抬高 p（少走弯路） | 反馈已有，写回半自动 |
| best-of-n（每轮 k 个候选） | 放大 n | 未实现，收益最大 |
| 重复运行取 success@k | 度量而非提升 | 需纳入评测 |

粗算：当前 p≈0.33，k=3 → 约 70%；若规格锚点把 p 提到 0.5，k=3 → 约 87%。
**这不是理论空谈**：CyberGym 上同一模型 2 美元预算 28.9%，放到 30 次尝试是 66.7%。

## 6. 迁移路径（不推翻已有工作）

1. **已完成**：后端注册表 + `windows_native` 后端 + `NEEDS_BACKEND` 诊断
   （`src/backends.py`，驱动 tier 不再假装在容器里执行）；
2. **下一步**：给 0107 建带 `target_profile` 的规格，用
   `--tier driver_userland --allow-native` 跑第一个驱动样本；
3. **再下一步**：kernel tier 上 VM 快照后端（Hyper-V checkpoint + revert），
   在此之前一律拒绝执行——保命优先；
4. **并行**：`--candidates k` 与 `success@k` 统计，先出曲线再谈优化。

## 7. 风险与边界

- **原生执行共享本机**：`allow_native` 默认关闭，必须显式打开；一次探测一个值。
- **kernel 一律拒绝**：没有快照就没有 kernel 执行（`select()` 直接返回 None）。
- **后端不等于能力**：有 Windows 后端不代表能进 D3D 路径，入口条件仍要靠规格描述。

## 8. 一句话

架构改造的实质是**把三个写死的假设变成三个可声明的属性**（平台、媒介、信号）。
声明得出来，就能做；声明不出来，系统会明确说 `NEEDS_BACKEND`，
而不是像以前那样报一个看起来像"模型不行"的 `NOT_VERIFIED`。
