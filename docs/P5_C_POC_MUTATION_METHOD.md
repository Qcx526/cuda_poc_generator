# P5-C PoC 变异：一套可复现的方法及其定位

报告语言：`zh-CN`。本文定义"PoC 变异"在本工程中的确切含义、与已有工作的差异、
可主张的创新点，以及当前实现到了哪一步（**方法与实现严格分开陈述**，避免把设计说成结果）。

## 1. 定义

**PoC 变异**：以一个**已通过归属判定**的 PoC（或经确认的良性样本）为种子，
在**由规格显式声明的变异轴**上做单点改动，采集每次运行的**效应指纹**，
据此判定结果是"同一个 bug"、"新 bug"还是"同一 bug 的更强原语"。

三个要素缺一不可：

| 要素 | 作用 | 缺失后果 |
|---|---|---|
| 种子须已验证 | 保证起点确实触发了目标机制 | 变异的都是在"不知道是什么"的崩溃上 |
| 变异轴须声明 | 保证可复现、可审计、可消融 | 退化为随机 fuzz，结果无法归因 |
| 效应指纹须分级 | 区分"同一 bug 的不同表现"与"新 bug" | 十个表现被当成十个漏洞 |

## 2. 与已有工作的差异

| 工作 | 做了什么 | 与我们的区别 |
|---|---|---|
| **AFL 系 fuzzing** | 变异输入找崩溃，覆盖率引导 | 目标是"找到崩溃"，不判断是否为新 bug，也没有"已验证种子"这一前提 |
| **崩溃去重**（Electronics 2024，Intel PT + 模糊哈希） | 把重复崩溃聚成一组，比栈哈希准确率高 15.38% | 解决"噪声太多"，但只在**崩溃集合内部**做聚类；不产出"这是新漏洞"的结论，也不回灌生成 |
| **JSGo**（CCS'24） | 用测试套件 + 踪迹引导变异，验证已知漏洞（26 个中复现 20 个） | 变异服务于**验证**已知漏洞，不用于发现新漏洞 |
| **Revery / FUZE**（CCS'18） | 从 PoC 出发找可利用状态，layout-oriented fuzzing，拼接崩溃路径与分叉路径 | 目标最强（生成 EXP），但依赖 angr 符号执行、针对用户态堆；**不处理"这次崩溃是不是新 bug"** |
| **CVE-Genie**（arXiv 2509.01835, 2025） | LLM 多智能体端到端复现 CVE，841 个中复现 428 个（51%） | 停在"复现成功"；没有从 PoC 继续向外探索的环节 |

**空白**：没有工作把"已验证 PoC"当作**种子**，用**规格声明的语义轴**做变异，
并用**分级效应指纹**去判定"新 bug / 同一 bug / 更强原语"，再把结果回灌给生成端。

## 3. 方法（五步）

### 步骤 1：种子确立

种子必须满足三条件（良性干净 / 触发崩溃 / 对照干净）。
不满足的样本不进变异流程，直接进"未归属崩溃库"（`data/findings/novel/`）。

### 步骤 2：变异轴声明

由规格声明，不由模型自由选择：

```json
"mutation": {
  "seed": "poc_sh_size_0.cubin",
  "axes": [
    {"name": "boundary",  "field": "sh_size",   "values": [0, 1, 11, 12, 23, 24, 48]},
    {"name": "mechanism", "field": "sh_type",   "values": [1, 2, 3, 4]},
    {"name": "structure", "field": "sh_offset", "values": [0, 1, 257, 4096]}
  ],
  "required": ["boundary", "mechanism"]
}
```

- **边界轴**：探 oracle 条件的两侧（0/11 崩，12/24 不崩）
- **机制轴**：回退到"不触发该机制"的取值，用来**证伪**归属
- **结构轴**：改相邻字段，探同一解析器内的其他分支

`required` 声明哪些轴必须覆盖；缺轴时判定最高为 `NOT_VERIFIED`。

### 步骤 3：效应指纹采集

分三级，逐级增强判定力：

| 级别 | 采集内容 | 能回答 |
|---|---|---|
| **L0** | 退出码 | 崩没崩 |
| **L1** | + 崩溃模块与偏移（栈顶帧） | 是不是同一处 → **能判"新 bug"** |
| **L2** | + 故障类型（读/写）、故障地址、输出差异 | 有没有更强原语 → **能判"利用潜能"** |

指纹形式：`H(tool, module, offset_bucket, fault_type)`，`offset_bucket` 按 4 KB 取整，
以容忍同一天然差异但区分不同函数。

### 步骤 4：新颖性判定

```
for 每个变异体:
    指纹 = 采集()
    if 指纹 == 种子指纹:        丢弃（同一个 bug）
    elif 指纹 in 已知集合:      归并（已记录过）
    else:                      标记 NOVEL → 入库待分诊
```

**关键**：判定依据是**指纹不相等**，不是"崩了"。这条替换掉现在的"崩即记录"。

### 步骤 5：沉淀与回灌

- `NOVEL` 结果进 `data/findings/novel/`，带 `fingerprint` 与触发它的最小变异描述
- 人工分诊后（`triage` 字段）分为：真新漏洞 / 同一 bug 的变体 / 误报
- 分诊结论回灌 RAG：让下一轮生成知道"这个字段已被证明会崩在 X 处"

## 4. 可主张的创新点

每条都标注"为什么已有工作没做"与"怎么证明"。

### C1：变异轴的**规格化**

> 变异不是模型或 fuzzer 的自由行为，而是规格里可审计、可复现、可消融的声明。

- 已有工作：AFL 的变异策略是通用的（位翻转/算术/拼接），不针对某个漏洞的语义；
  Revery 的变异由 layout 引导，但仍不声明"轴"。
- 证明：消融实验——去掉 `required` 约束后，新指纹率与误报率的变化。

### C2：效应指纹分级，使"新 bug"可判定

> 把可观测量从"崩溃"升级为"崩溃点 + 故障类型 + 地址"，才能区分同一 bug 的多种表现。

- 已有工作：崩溃去重只在崩溃集合内聚类，不产出"新漏洞"结论；Revery 关心可利用状态但不关心是否新 bug。
- 证明：同一批变异体，用 L0 与 L1/L2 判定，统计"被判为新 bug 但实际同源"的比例。

### C3：变异结果**回灌生成**的闭环

> 变异的产物不是报告，而是下一轮生成的约束。

- 已有工作：CVE-Genie 停在复现；fuzzing 的崩溃库不回流到 PoC 生成。
- 证明：有/无回灌两组，比较第二轮生成的成功率。

## 4.1 NOVEL_SITE 已在真实目标上验证

在 CVE-2024-0076 上把结构轴加进来（段表项数、节名表索引），三种结果同时出现：

| 变体 | 崩溃点 | 判定 |
|---|---|---|
| 种子（`sh_size=0xFFFFFFFF`） | `cuobjdump+0xb000` | — |
| `sh_size=0x10` | 不崩 | `CLEAN` |
| `e_shnum=1` | **`cuobjdump+0x12000`** | `NOVEL_SITE` |
| `e_shnum=4096` | **`libc.so.6+0x183000`** | `NOVEL_SITE` |

两条新点位按指纹去重后自动进入 `data/findings/novel/`，状态 `UNTRIAGED`。

**取证结论（valgrind memcheck）**：

| 发现 | memcheck | 判断 |
|---|---|---|
| `cuobjdump+0x12000` | `Invalid read of size 4 at 0x4` | 读 `NULL+4`，空结构体成员访问 |
| `libc.so.6+0x183000` | `Invalid read of size 1 at 0x0`，栈在 `strcmp` | 节名为 NULL 时未检查就 `strcmp` |

**两者都是空指针读，不是堆破坏。** 这否证了"崩在 libc 就是内存破坏"的直觉，
也说明 `NOVEL_SITE` 能找到新位置，但**位置新不代表更严重**——
严重程度必须由 memcheck 或读写类型单独判定，不能从崩溃点推断。

## 4.2 C3 的实验结果：回灌会放大错误

设计：同一 CVE、同一预算，A 组（无实测知识）与 B 组（注入变异结论）各跑一次闭环。

| 组 | 知识 | 结果 | 迭代 |
|---|---|---|---|
| A | 无 | `EXHAUSTED` / `NOT_VERIFIED` | 2 |
| A' | 无（RAG 依赖已装但未注入） | `EXHAUSTED` / `NOT_VERIFIED` | 2 |
| **B** | **注入 23340 的变异结论** | **`SUPPORTED`** | 2 |

看起来是"知识有用"，但独立复核后**不成立**：

B 组产出的 `poc_sh_size_0.cubin` 把**第 1 节**（`e_shstrndx=1` 指向的字符串表，原 type=3 size=236）
的 `sh_size` 改成了 0，nvdisasm 在解析节名时读到空表而崩。

**这与 CVE-2025-23340 的 RELA 对齐缺陷无关**，和之前那次假阳性是同一个形状。
而知识条目里那句"触发窗口是 `sh_size` ∈ [0]"正是从那次假阳性推出来的——
**回灌把错误结论教给了下一轮，并且被三条件判分接受。**

### 由此得到的三条修正

1. **知识条目必须标注归属状态**。机制轴不区分时，条目只描述现象，不得写成"取这个值"。
   已实现 `attributed()`，未确证归属的条目开头明确写出警告。
2. **判分需要机制轴对照**，而不只是候选自选的 controls（见 §4.4）。
3. **回灌的价值取决于种子的正确性**：种子若是假阳性，回灌会稳定地复制它。

C3 的主张因此要收窄：回灌能传递结论，但它同时会传递错误；
在没有归属校验之前，不能声称"回灌提升成功率"。

## 6. 评测设计

| 编号 | 问题 | 设计 | 指标 |
|---|---|---|---|
| E1 | 能否发现新东西 | 在 N 个已验证 PoC 上跑全轴变异 | 新指纹数、人工确认为新 bug 的数量 |
| E2 | 指纹是否比栈哈希准 | 同一批变异体，两种去重对照 | 同源误判率（越低越好） |
| E3 | 是否比盲 fuzz 划算 | 同等时间预算下与 AFL 对比 | 单位时间新指纹数 |
| E4 | 各轴贡献 | 逐个去掉 boundary / mechanism / structure | 新指纹数下降幅度 |
| E5 | 能否识别假阳性 | 复现 CVE-2025-23340 那次假阳性案例 | 是否能判为"同一 bug"而非新漏洞 |

**E5 是现成的 case study**：我们已实测——`poc_sh_size_0` 崩、还原 `sh_size=24` 不崩，
但把 `sh_type` 改成 PROGBITS **仍然崩**，说明崩溃来自被破坏的字符串表而非 RELA 处理器。
一个只做边界轴的变异会把这里误判为"复现成功"。

## 7. 汇报骨架（一页一节）

1. **问题**：LLM 能生成 PoC，但"生成了一个崩溃"和"发现了一个漏洞"之间没有判定
2. **现状**：复现（CVE-Genie）、可利用性（Revery）、去重（Electronics'24）各自解决一段
3. **空白**：没有把已验证 PoC 当种子、按语义轴变异、用指纹判新颖性的方法
4. **方法**：五步（种子 → 轴 → 指纹 → 新颖性 → 回灌）
5. **创新**：C1 轴规格化 / C2 指纹分级 / C3 回灌闭环
6. **证据**：假阳性案例（23340）+ 当前实现度 + 评测计划
7. **限制**：L1/L2 未实现，结论只到"能判崩溃不能判新颖"
