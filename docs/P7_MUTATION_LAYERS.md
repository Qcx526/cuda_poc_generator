# 复现之后的变异：层面、流程、判定

对一个**已复现**的 PoC，按固定的层面顺序做变异，把「这个 PoC 附近还有没有别人没解释的问题」
变成一个可重复的流程，而不是每次重新设计实验。

## 一、七个层面

一个 cubin 里实际存在的东西决定了可以改什么：

```
.shstrtab  .strtab  .symtab  .debug_frame  .nv.info  .nv.info.<kernel>
.nv.rel.action  .rel.debug_frame  .nv.constant0.<kernel>  .text.<kernel>
```

| # | 层面 | 改什么 | 想打到什么 | 现状 |
|---|---|---|---|---|
| 1 | 字节级 | 任意位置翻字节 | 算术与拷贝 | 有，**实测几乎无效**（124 变体 0 崩溃） |
| 2 | 字段值级 | 数值字段代入边界值 | 边界检查、类型分派 | **有，主力**（689 变体） |
| 3 | 字段关系级 | 值取自另一个字段，破坏自洽 | 交叉校验、索引到表 | **有**（82 变体） |
| 4 | 结构布局级 | 截断、填充、移动/扩写节表 | 数组遍历、表项读取 | **有**（13 变体） |
| 5 | 容器级 | fatbin / 目标文件包装、多 cubin 共存 | 容器解析、成员提取 | 未实现 |
| 6 | 载荷语义级 | 节**内部**的记录：符号表项、`nv.info` 属性、重定位项、CFI | 各记录类型的解析器 | 未实现 |
| 7 | 命名级 | `strtab`/`shstrtab` 内容：空名、重名、不结尾、偏移越界 | 名字解析、`strlen` | 未实现 |

**顺序不是随意的**：成本 1 ≪ 2 < 3 ≪ 4 < 5 < 6，而收益在第 1 层已证伪。所以流程从第 2 层开始。

第 3 层是新增的重点。它问的是第 2 层问不出的问题：

| 关系 | 变异 | 语义 |
|---|---|---|
| `sh_offset + sh_size == 文件长` | 令 `sh_size = 文件长 - sh_offset` | 正好覆盖到文件尾 |
| 同上 | `+8` | 差一点就覆盖到，边界感最强 |
| `sh_entsize == 记录长度` | 令 `sh_entsize = 12` | 步长小于重定位项对齐要求 |
| `sh_link < e_shnum` | 令 `sh_link = e_shnum` | 索引越界一格 |
| `sh_name < strtab 大小` | 令 `sh_name = strtab 大小` | 名字偏移刚好越界 |

## 二、流程

对每个复现的 PoC：

```bash
python -m src.mutate --cve <CVE> --seed <PoC> \
    --image <镜像> --tool "cuobjdump --dump-elf {artifact}" \
    --workdir <输出目录>
```

```
① 建图    解析节表与字段表，报告里列出"这个文件有什么"
② 值域    第 2 层，边界值代入
③ 关系    第 3 层，不变量驱动的有序对
④ 判定    崩溃点查台账 → 新 / 已知；新点连同触发配方一起登记
⑤ 交付    mutation_report.md
```

每层单独跑、单独统计，因为**层与层的产出不可比**：689 个变体打中 2 个点，
和 82 个变体打中 2 个点，说的是完全不同的两件事。

## 三、报告长什么样

```markdown
## 结构
| # | 节 | 类型 | 大小 |

## 覆盖的层面
| 层面 | 变体 | 拒绝 | 与种子同处 | 新点位 | 崩溃点 | 新 | 已知 |
| value    | 689 | 196 | 0 | 16 | 2 | 2 | 0 |
| relation |  82 |  36 | 0 |  2 | 2 | 2 | 0 |

## 跳过的层面
- layout：尚未实现：需要重写节表与文件长度的写入器

## 崩溃点
| 崩溃点 | 判定 | 归属 |
```

**「跳过了哪几层、为什么」必须写。** 否则一份「无新发现」的报告无法区分是
「真的探完了」还是「只做了第一层」。

## 四、四个数字必须分开

同一份种子上，这几个数经常被混为一谈：

| 数字 | 含义 | 混掉的后果 |
|---|---|---|
| 变体数 | 成本 | — |
| 拒绝数 | 语义合法性 | 拒绝率高说明变异没被解析到，出 0 崩溃不代表安全 |
| **与种子同处** | 变异没改变行为 | 种子本身在崩时，这类会淹没真正的信号 |
| 新点位 | 真正的新信息 | 只有这个值钱 |

实测：用已崩的 PoC 做种子，688 个变体里 666 个"崩"，全是种子那一处——
如果只看"崩溃数"，会得出"变异极其有效"的错误结论。

## 五、台账：让"新"变成查表

`data/mutation/sites.json` 记录每个崩溃点：首次出现在哪、哪个 CVE、哪个工具、各版本崩不崩。

```json
"cuobjdump+0x68000": {
  "cve": "CVE-2024-0076", "tool": "cuobjdump", "first_source": "value",
  "versions": {"cuda:12.4.1": true, "cuda:13.0.0": false}
}
```

没有台账时，「这个偏移见过没有」靠人记；有台账后是 `site in ledger` 一个判断。
**这是流程能重复的前提**：每个 PoC 走完都往里写，后一个 PoC 才知道哪些点已被解释。

## 六、实测记录

| 运行 | 种子 | 镜像 | 层面 | 结果 |
|---|---|---|---|---|
| layers-124 | 12.4 能解析的良性 cubin | 12.4 | 值域 + 关系 | 771 变体 → **4 个新崩溃点** |

四个点是 `cuobjdump+0x66000/+0x67000/+0x68000`、`libc+0xa5000`，
与独立跑 757 变体值穷举得到的集合**完全一致**——流程没有漏，也没有多报。

## 七、每个崩溃点都存一条可重建的配方

台账里每个点除了指纹和版本，还存了**触发它的编辑**——绝对偏移、位宽、值：

```json
"cuobjdump+0x68000": {
  "triggers": [{"stage": "value", "edits": [[1688, 8, 0]],
                "fields": {"sec4.sh_offset": 0},
                "seed_sha256": "9f2c1a7b3e5d0c41"}]
}
```

为什么必须存：变体文件在临时目录里，通常早就清掉了。没有配方时，想回答
「`+0x68000` 是哪个变异打出来的」只能翻几百个文件——而且已经翻不到了。

重建：

```bash
python -m src.replay --site cuobjdump+0x68000 --seed <cubin> \
    --image <镜像> --tool "cuobjdump --dump-elf {artifact}"
```

```
重建 replay_cuobjdump_0x68000.cubin（2536 字节，1 处编辑）
退出码 139 | 崩溃点 cuobjdump+0x68000
一致：重建的文件崩在同一处
```

`seed_sha256` 前 16 位对不上时直接拒绝——偏移是对的，但种子不是同一份，
重放出来的是另一件事。

实测台账里的五条：

| 崩溃点 | 阶段 | 触发 |
|---|---|---|
| `cuobjdump+0x66000` | value | `sec5.sh_size = 0xFFFFFFFFFFFFFFFF` |
| `cuobjdump+0x67000` | value | `sec3.sh_type = 0` |
| `cuobjdump+0x68000` | value | `sec4.sh_offset = 0` |
| `libc.so.6+0xa5000` | value | `sec4.sh_size = 0xFFFFFFFFFFFFFFFF` |
| `libc.so.6+0x19d000` | value | `sec8.sh_offset = 8` |

**一行一个**，这就是「哪个变异触发了哪个点」的答案。

## 七点五、第 4 层：结构布局

改的不是字段值，是**文件的形状**。13 个变体：

| 操作 | 数量 | 具体 |
|---|---|---|
| 截断 | 7 | 在 63 / 64 / 1268 / 1663 / 1664 / 1665 / 2535 处切断 |
| 填充 | 3 | 尾部加 1 / 64 / 4096 字节 |
| 移动节表 | 1 | 把节表复制到文件尾，`e_shoff` 指向副本 |
| 扩写节表 | 2 | 复制到尾部后追加 1 / 8 个空表项，`e_shnum` 同步增加 |

### 11.2 与 12.4 的差别非常干净

| 变体 | 11.2 | 12.4 |
|---|---|---|
| 6 个截断 | **全部崩溃**（`libc.so.6+0x183000`，exit 139） | **全部被拒**（exit 255） |
| 3 个填充 | 无影响（exit 0） | 无影响 |
| 移动节表 | 无影响 | 无影响 |
| 扩写节表 | 无影响 | 无影响 |

**截断是这一层唯一有效的变异，而 12.4 恰好在这一处加上了校验**：
读之前先检查文件长度够不够。填充和移动节表两个版本都能容忍。

### 一个诚实的保留

崩在 `libc.so.6+0x183000` 意味着**故障指令不在 cuobjdump 里**，很可能是一次短读之后
把截断的缓冲区当成完整数据去拷贝。这是真崩溃，但归因弱：它说明"cuobjdump 没检查长度"，
不说明是哪段逻辑算错了。

而且这个点位本身不稳定——第 3 层里同一地址在不同运行中时有时无。

## 八、跨版本验证接进流程

发现新点后不用再手工跑第二遍，`--versions` 一次给完：

```bash
python -m src.mutate --cve CVE-2024-0076 --seed <cubin> \
    --image nvidia/cuda:12.4.1-devel-ubuntu22.04 \
    --versions "nvidia/cuda:12.4.1-devel-ubuntu22.04,nvidia/cuda:13.0.0-devel-ubuntu24.04" \
    --tool "cuobjdump --dump-elf {artifact}" --workdir <输出>
```

每个新点按配方重建，逐镜像重跑，判定三种结果：

| 结果 | 含义 |
|---|---|
| **最新版仍崩（候选新漏洞）** | 唯一值得往下走的情况 |
| 已修复（X 起不崩） | 已披露或已修未公开，需查重 |
| 各版本均未崩 | 跨版本重建失败，配方或种子有问题 |

实测报告（12.4 → 13.0，4 个点）：

```
| cuobjdump+0x67000 | 新 | 12.4.1 崩; 13.0.0 不崩 | 已修复（13.0.0 起不崩） |
| cuobjdump+0x68000 | 新 | 12.4.1 崩; 13.0.0 不崩 | 已修复（13.0.0 起不崩） |
| cuobjdump+0x66000 | 新 | 12.4.1 崩; 13.0.0 不崩 | 已修复（13.0.0 起不崩） |
| libc+0xa5000      | 新 | 12.4.1 崩; 13.0.0 不崩 | 已修复（13.0.0 起不崩） |
```

### 一个稳定性问题

同一份种子、同一批变异，两次运行分别得到 **5 个**和 **4 个**崩溃点，
差的是 `libc.so.6+0x19d000`（`sec8.sh_offset = 8`）。

**libc 里的崩溃点不稳定。** 故障指令虽然固定，但走到哪个 libc 函数取决于堆布局，
同一个变异在不同运行里可能落进不同的拷贝/释放路径。

后果：`libc.*` 的点用于判定"有没有新发现"时不可靠，应优先看目标程序内部
（`cuobjdump+` / `nvdisasm+`）的点。台账目前没有区分这一点——已知缺口。

## 九、还没做的

- 第 4/5/6/7 层只有名字与跳过理由，没有实现
- 跨版本验证（12.4 → 13.0）仍是单独命令，没有接进本流程
- 台账只按 `module+offset` 去重（4 KB 取整），同一桶内不同性质的两个缺陷会被合并；
  访问类型（读/写）已记录在发现里，但台账还没有用它做二次区分
