# 复现之后的变异：层面、流程、判定

对一个**已复现**的 PoC，按固定的层面顺序做变异，把「这个 PoC 附近还有没有别人没解释的问题」
变成一个可重复的流程，而不是每次重新设计实验。

## 一、七个层面

一个 cubin 里实际存在的东西决定了可以改什么：

```
.shstrtab  .strtab  .symtab  .debug_frame  .nv.info  .nv.info.<kernel>
.nv.rel.action  .rel.debug_frame  .nv.constant0.<kernel>  .text.<kernel>
```

| # | 层面 | 改什么 | 想打到什么 | 现状 |
|---|---|---|---|---|
| 1 | 字节级 | 任意位置翻字节 | 算术与拷贝 | 有，**实测几乎无效**（124 变体 0 崩溃） |
| 2 | 字段值级 | 数值字段代入边界值 | 边界检查、类型分派 | **有，主力**（689 变体） |
| 3 | 字段关系级 | 值取自另一个字段，破坏自洽 | 交叉校验、索引到表 | **有**（82 变体） |
| 4 | 结构布局级 | 增删节、截断、错位节表 | 数组遍历、表项读取 | 未实现 |
| 5 | 容器级 | fatbin / 目标文件包装、多 cubin 共存 | 容器解析、成员提取 | 未实现 |
| 6 | 载荷语义级 | 节**内部**的记录：符号表项、`nv.info` 属性、重定位项、CFI | 各记录类型的解析器 | 未实现 |
| 7 | 命名级 | `strtab`/`shstrtab` 内容：空名、重名、不结尾、偏移越界 | 名字解析、`strlen` | 未实现 |

**顺序不是随意的**：成本 1 ≪ 2 < 3 ≪ 4 < 5 < 6，而收益在第 1 层已证伪。所以流程从第 2 层开始。

第 3 层是新增的重点。它问的是第 2 层问不出的问题：

| 关系 | 变异 | 语义 |
|---|---|---|
| `sh_offset + sh_size == 文件长` | 令 `sh_size = 文件长 - sh_offset` | 正好覆盖到文件尾 |
| 同上 | `+8` | 差一点就覆盖到，边界感最强 |
| `sh_entsize == 记录长度` | 令 `sh_entsize = 12` | 步长小于重定位项对齐要求 |
| `sh_link < e_shnum` | 令 `sh_link = e_shnum` | 索引越界一格 |
| `sh_name < strtab 大小` | 令 `sh_name = strtab 大小` | 名字偏移刚好越界 |

## 二、流程

对每个复现的 PoC：

```bash
python -m src.mutate --cve <CVE> --seed <PoC> \
    --image <镜像> --tool "cuobjdump --dump-elf {artifact}" \
    --workdir <输出目录>
```

```
① 建图    解析节表与字段表，报告里列出"这个文件有什么"
② 值域    第 2 层，边界值代入
③ 关系    第 3 层，不变量驱动的有序对
④ 判定    崩溃点查台账 → 新 / 已知
⑤ 交付    mutation_report.md
```

每层单独跑、单独统计，因为**层与层的产出不可比**：689 个变体打中 2 个点，
和 82 个变体打中 2 个点，说的是完全不同的两件事。

## 三、报告长什么样

```markdown
## 结构
| # | 节 | 类型 | 大小 |

## 覆盖的层面
| 层面 | 变体 | 拒绝 | 与种子同处 | 新点位 | 崩溃点 | 新 | 已知 |
| value    | 689 | 196 | 0 | 16 | 2 | 2 | 0 |
| relation |  82 |  36 | 0 |  2 | 2 | 2 | 0 |

## 跳过的层面
- layout：尚未实现：需要重写节表与文件长度的写入器

## 崩溃点
| 崩溃点 | 判定 | 归属 |
```

**「跳过了哪几层、为什么」必须写。** 否则一份「无新发现」的报告无法区分是
「真的探完了」还是「只做了第一层」。

## 四、四个数字必须分开

同一份种子上，这几个数经常被混为一谈：

| 数字 | 含义 | 混掉的后果 |
|---|---|---|
| 变体数 | 成本 | — |
| 拒绝数 | 语义合法性 | 拒绝率高说明变异没被解析到，出 0 崩溃不代表安全 |
| **与种子同处** | 变异没改变行为 | 种子本身在崩时，这类会淹没真正的信号 |
| 新点位 | 真正的新信息 | 只有这个值钱 |

实测：用已崩的 PoC 做种子，688 个变体里 666 个"崩"，全是种子那一处——
如果只看"崩溃数"，会得出"变异极其有效"的错误结论。

## 五、台账：让"新"变成查表

`data/mutation/sites.json` 记录每个崩溃点：首次出现在哪、哪个 CVE、哪个工具、各版本崩不崩。

```json
"cuobjdump+0x68000": {
  "cve": "CVE-2024-0076", "tool": "cuobjdump", "first_source": "value",
  "versions": {"cuda:12.4.1": true, "cuda:13.0.0": false}
}
```

没有台账时，「这个偏移见过没有」靠人记；有台账后是 `site in ledger` 一个判断。
**这是流程能重复的前提**：每个 PoC 走完都往里写，后一个 PoC 才知道哪些点已被解释。

## 六、实测记录

| 运行 | 种子 | 镜像 | 层面 | 结果 |
|---|---|---|---|---|
| layers-124 | 12.4 能解析的良性 cubin | 12.4 | 值域 + 关系 | 771 变体 → **4 个新崩溃点** |

四个点是 `cuobjdump+0x66000/+0x67000/+0x68000`、`libc+0xa5000`，
与独立跑 757 变体值穷举得到的集合**完全一致**——流程没有漏，也没有多报。

## 七、还没做的

- 第 4/5/6/7 层只有名字与跳过理由，没有实现
- 台账目前只记指纹与版本，没有记"触发它的字段组合"（下一步应补，否则复现一个点要回翻变体文件）
- 跨版本验证（12.4 → 13.0）仍是单独命令，没有接进本流程
