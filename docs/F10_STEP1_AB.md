# F10-Step1：CUDA 真实工具链上的 V2 效果评估

基线 `416edc4`。目标：CVE-2025-23340（nvdisasm，CUDA 11.2.2），A/B 各一次真实生成 + 真实执行。

## 一、实验设置

| 项 | 值 |
|---|---|
| 模型 | 同一 Provider、同一配置、温度 0 |
| 任务提示 | **两组完全相同**（1964 vs 556 字符的差异只来自输入块） |
| 工具 | 容器 `cpg/cuda112-py3:1.0` 内的 `nvdisasm`（Built Feb 2021，CUDA 11.2.2） |
| 对照 | `demo/CVE-2024-0076/artifacts/benign.cubin` → **exit 0** |
| 预算 | 每组 1 次调用、1 个候选，无重试 |
| A 组输入 | `spec.prompt_brief()`（`CPG_BLIND_CONTRACT=1`，F7 修复后的旧投影） |
| B 组输入 | V2 Case → `build_context(PUBLIC_ONLY)` 的 payload |
| 泄漏检查 | 两组 Prompt 均不含 `sh_size` / `1..11` / `24 的倍数` / `attack_vector` |

**必须声明的混杂因素**：两组输入**格式不同**（纯文本 vs JSON），长度 556 vs 1964 字符。
因此差异不能全部归因于"V2 的语义结构"，也可能来自长度与呈现方式。

## 二、结果

| 指标 | A（旧七维盲投影） | B（V2 PUBLIC_ONLY） |
|---|---|---|
| A. 输入有效、无泄漏 | 是 | 是 |
| B. 识别入口/组件/格式 | 是（代码含 nvdisasm、ELF、RELA） | 是（同） |
| C. 约束有来源 / 幻觉 | 无据断言：无；无编造内核地址 | 同；地址均为自选 ELF 布局偏移 |
| D. 候选可执行 | **否**：脚本自身 `struct.error`，未跑到工具 | 是 |
| E. 实际执行到 nvdisasm | **否** | **是** |
| F. 可重复的可区分异常 | 无 | **无**：`EXIT=1`（干净拒绝），对照 exit 0 |
| G. 成本 | 1 次调用 | 1 次调用 |
| 级别 | GENERATED / EXECUTED（工具未运行） | GENERATED / EXECUTED（工具拒绝） |

产物：`data/driver/f10step1/{A,B}/{prompt.txt,response.txt,candidate.py,run.log}`、
`summary.json`、`evaluation.json`。

### 2.1 A 组为什么失败

```
struct.error: pack_into requires a buffer of at least 1073536 bytes
              for packing 64 bytes at offset 1073472 (actual buffer size is 1073534)
```

它把节头表偏移算早了两个字节。**这是模型自己的实现错误**，与输入表示无关，也不能算"工具链问题"。

### 2.2 B 组为什么不算命中

`nvdisasm` 返回 **1**，不是 139/信号。按既定判据：

- `exit ∈ [1,127]` = **干净拒绝**，不是崩溃；
- 良性对照 `exit 0`，说明工具本身正常；
- 没有单字段对照、没有可复现异常 → **不构成 `OBSERVED_ANOMALY`**，更不构成 `VULNERABILITY_VERIFIED`。

我在运行脚本里最初把 `exit != 0` 都当作异常，那是错的（正是审计反复提醒的"用退出码冒充命中"），
已改为 `exit >= 128 或 < 0` 才算异常，并据此重判——**没有重新生成**。

## 三、三个问题

**1. V2 是否减少了无关或误导性输入？**
**没有观察到。** 两组输入都不含历史配方，A 甚至更短（556 字符）。
V2 增加的是结构与显式授权，不是"更少噪音"。

**2. V2 是否帮助模型产生更准确、可验证的漏洞约束？**
**本组数据无法支持。** 任务只要求输出代码，模型没有给出可引用的约束条目，
所以"C"只能从代码侧看：两组都识别了 nvdisasm / ELF / SHT_RELA，都没有编造内核地址。
**看不出 V2 的优势，也看不出劣势。**

**3. V2 是否真正改善候选 PoC 的有效性？**
**在一个可观测维度上是：B 的候选能跑起来，A 的不能。** 但差距来自 A 的缓冲区算术 bug，
属于实现质量，不是语义理解。**在"触发目标缺陷"这个真正的目标上，两组都是零。**

## 四、结论（如实）

- 单组配对（n=1）、无重复，**不足以支撑"V2 更好"或"V2 更差"**；
- 唯一可量化的差别：B 的 harness 可执行、A 的有实现错误；
- 两组都未触发目标 CVE，`VULNERABILITY_VERIFIED = 0`；
- 不修改评价标准、不重复生成追求正结果。

## 五、若要继续，缺什么

1. **n 要大**：至少 5 组配对，才能把"实现 bug"与"表示差异"分开；
2. **任务要能产出约束**：让模型先输出"触发约束 + 证据引用"，再输出代码，才能测 C 指标；
3. **判据要更细**：需要 `nvdisasm` 的 stderr 分类（拒绝原因），才能判断 exit=1 是"格式校验失败"还是"参数校验失败"。

## 六、边界

未重跑 CUDA CVE、未改 P11/P12、未执行内核 Escape、未扩建 Mock；
两组均未收到历史 PoC 或触发配方；模型调用共 2 次。
