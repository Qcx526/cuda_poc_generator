# P4-Q 工程状态评估：离"全自动闭环出报告"还差多远

报告语言：`zh-CN`。评估时间：2026-10-22。所有数字均来自本仓库实际运行记录。

## 1. 先回答核心问题：链路闭了吗？

**闭了。** 输入 → 生成 → 执行 → 差分判定 → 诊断 → 反馈 → 再生成 → 报告，
每一个环节都有真实运行记录，且每个环节都修过由真实运行暴露的缺陷。

**但"闭了"不等于"好用"**——差的是三个量：稳定性、覆盖面、证据深度。

**综合：约 65–70%。** 链路全通，短板集中在"稳定性"和"覆盖面"。

## 3. 三个差距，按致命程度排

### 差距一：单次成功率只有 ~1/3（最致命）

同一 CVE 两次运行可以一次 `SUPPORTED` 一次 `NO_EFFECT`（0076 实测 2/6）。
**不解决这个，任何"成功率"数字都不可信，论文结论站不住。**

数学很清楚：p≈0.33 时取 3 个独立候选约 70%；规格锚点把 p 抬到 0.5 则约 87%。
对应两个改动：`--candidates k`（best-of-n）与 success@k 度量。

### 差距二：覆盖面只有工具链一类

- 工具链：9/15 至少一次成功 ✅
- 驱动（用户态）：全流程已通（0107 走到 D3D9 提交），0 个成功 ⚠️
- 内核：拒绝执行（无 VM 快照后端）❌
- 库/服务类（nvJPEG/Triton/CV-CUDA）：架构支持（api_sequence/packet 媒介），未试 ⚠️

### 差距三：证据深度停在"支持"而非"已验证"

评级能证明"受控样本崩 + 基线净 + 对照干净"，但没有寄存器级/根因级证据，
版本门几乎恒为"未知"。这在论文里会被追问："你怎么确定崩的就是这个 CVE？"

## 5. 一句话

**框架已经是一个能自动迭代的闭环系统，不是原型**；
现在的差距是"把 1/3 的单次成功率变成可信的组合成功率，并把能力从工具链
扩展到驱动与内核"。这两件事都不需要推翻任何现有设计——P0 的两项加起来
不到三天，就能让论文的核心实验数字成立。
