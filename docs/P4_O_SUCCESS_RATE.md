# P4-O 成功率的瓶颈与改进路线

报告语言：`zh-CN`。基于 15 个工具链 CVE（2/6 次成功率）与 4 个驱动类 CVE（0 次）的实测。

## 1. 先说结论

| 类别 | 现状 | 根因 |
|---|---|---|
| 工具链 15 个 | 6 个 `SUPPORTED`，但单次成功率约 1/3 | 模型对"改哪个字段"的选择不稳定 |
| 驱动类 4 个 | **0 个** | **执行后端错配**：Windows 驱动目标被放进 Linux 容器 |

驱动类的问题不是"难"，是**根本跑不起来**。`nvcuda.dll` / `nvgpucomp64.dll` 在 Linux 容器里
连加载都做不到，任何候选都会在第一步失败。之前报的 `NOT_VERIFIED` 是假象。

已修：驱动 tier 现在直接返回 `PLATFORM_UNAVAILABLE`，不再伪造执行结果
（`src/closed_loop.py:docker_matrix_stage`）。**先诚实，再谈优化。**

## 2. 驱动类：从 0 到 1 需要补的三件事

### 2.1 Windows 原生执行后端（P0，必须做）

本机有 RTX 1660 + 驱动 617.42，`cdb.exe` 已就位。需要一条与工具链并行的执行路径：

```text
python main.py --cve-id ... --tier driver_userland
  └─ 在 Windows 宿主原生运行候选（不是容器）
       ├─ 采集 exit code / 异常模块 / 故障偏移
       ├─ 用 cdb 附加，确认是否命中目标函数（reached）
       └─ 超时/崩溃即停，单次探测，绝不批量重试
```

关键约束（沿用你之前定的铁律）：**一次探测一个值，触发即停**；
kernel tier 必须 VM + 快照，不能在本机裸跑。

### 2.2 驱动类的 EVS 需要新字段

工具链的 `input` 是文件，驱动的 `input` 是**调用序列 + 状态**：

| 新字段 | 含义 | 0107 的例子 |
|---|---|---|
| `entry_api` | 进入路径 | D3D 提交着色器 → `nvwgf2umx.dll` → `nvgpucomp64.dll` |
| `payload_form` | 载荷形态 | 着色器字节码（DXBC / legacy profile） |
| `state_sequence` | 前置调用序列 | CreateDevice → CreateVertexShader → … |
| `device_requirement` | 硬件/驱动前提 | GTX 1660 + 驱动 617.42（已确认） |
| `crash_oracle` | 崩溃判据 | 进程异常退出（非蓝屏） |

缺了 `entry_api` 与 `state_sequence`，模型只能猜"怎么把字节喂进去"，这正是 0107 反复
`PATH_NOT_REACHED` 的原因。

### 2.3 观测方式要换

工具链靠 exit code；驱动要看：进程退出码、故障模块名、cdb 的 `reached`。
kernel tier 还要加 WER / minidump / 事件日志，并且**以快照恢复为前提**。

## 3. 工具链：把 1/3 提到稳定

### 3.1 best-of-n（最直接，收益最大）

文献佐证：CyberGym 里同一模型在"2 美元预算"下 28.9%，放开到 30 次尝试变成 66.7%。
我们单次成功约 1/3，取 n=3 独立候选，理论上限到 1-(2/3)³ ≈ 70%。

实现代价：每次迭代多花 n-1 次生成（每次 5–12 分钟）。
建议做成 `--candidates k`，只在"距离成功只差一步"的 CVE 上开。

### 3.2 成功变异写回（已验证有效）

0076 第 4 次失败暴露"改了任意节"，把"第 8 节 + 巨大 sh_size 实测会崩"写回规格后，
第 6 次成功。这条要**自动化**：从观测日志里抽取"崩溃样本的变异点"，写进 `history`。

### 3.3 降低输入的不确定性

- prompt 里 `[EVS]` 摘要要保持短（现在已只放可执行事实）；
- 分析阶段固定温度 0（已做）；
- 同一 CVE 重跑时，把上次失败的变异点放进 `refuted`（已支持，待自动化）。

## 4. 评测方式必须改

现在的 2/6 说明：**单次结果是噪声**。论文应报告：

| 指标 | 定义 |
|---|---|
| `success@1` | 单次运行成功率（当前约 33%） |
| `success@3` | 三次独立运行至少一次成功 |
| 平均收敛轮数 | 成功样本平均用了几轮 |
| 假阳性率 | `SUPPORTED` 中人工复核不成立的比例 |

没有这四个数，任何"我们的方法有效"的结论都站不住。

## 5. 建议的执行顺序

1. **P0 驱动执行后端**（Windows 原生 + cdb）：不修这个，驱动类永远是 0；
2. **P1 等 0107 第一次跑通**后再谈优化——先拿到 1 个成功样本；
3. **P2 best-of-n**：工具链上验证 `success@k` 曲线，这本身就是论文的一张图；
4. **P3 变异点回写自动化**：把 0076 的手工操作变成流水线行为。

## 6. 一句话

驱动类的瓶颈是**环境**（没有 Windows 执行路径），工具链的瓶颈是**采样方差**（1/3 的单次成功率）。
前者必须补能力，后者用重复与 best-of-n 摊平——两者都不是提示词能解决的。
