# P4-L 文献调研：PoC 生成是怎么做的，我们该改什么

报告语言：`zh-CN`。调研时间为 2026-10-21，检索式包含 `LLM PoC generation`、
`vulnerability reproduction benchmark`、`one-day exploit generation`。

## 1. 四篇直接相关的工作

| 工作 | 任务 | 关键做法 | 报告结果 |
|---|---|---|---|
| **Zhao et al. 2025**（arXiv:2510.10148） | Web 漏洞 PoC，100 个 CVE，三阶段披露 | 只用公开信息 → 补代码上下文 → 自适应推理与提示精化 | 8–34% → 补上下文 +17–20%（函数级比文件级再 +9–13%）→ **提示精化后 68–72%** |
| **CyberGym**（arXiv:2506.02548） | 1507 个真实漏洞，188 个项目 | 智能体按执行反馈迭代；**成功判据 = 补丁前触发、补丁后不触发** | 最佳组合 11.9%；输入更丰富（栈回溯、ground-truth patch）显著提升；PoC >100 字节时成功率降到约 10% |
| **DIG**（arXiv:2606.13037） | 一日漏洞 PoC，138 个 CVE | 用 LLM 分析补丁，**合成显式 oracle**（触发所需前置条件），再按 oracle 求解约束 | 触发 80/138，比最佳基线高 40% |
| **ReX**（arXiv:2508.01371） | 智能合约 PoC | LLM 直接对接 Foundry 测试框架，生成即验证 | 最高 92% |

补充：**PoCEvolve**（补丁驱动的提示进化）报告了两个我们必须避开的坑——
上下文窗口被历史提示塞满、上游错误会污染整个循环。

## 2. 三条最硬的结论

### 2.1 显式化前置条件，比让模型"自己悟"强得多（DIG）

DIG 的核心不是更强的模型，而是把"触发需要什么条件"变成**可检查的 oracle**。
我们的失败分布正好印证：4 个 `NO_EFFECT` 都是"跑通了但没打中"，
根因是模型没有把"改哪个字段、为什么这个字段没被检查"显式说出来。

### 2.2 差分判据必须写进任务定义（CyberGym）

CyberGym 把"补丁前崩、补丁后不崩"作为**成功的定义**，而不是事后检查。
我们已经有恶意/良性/对照三类样本，但提示词里没把差分写成硬要求，
所以模型仍会产出"随便崩一下"的 PoC。

### 2.3 提示精化是最大杠杆（Zhao et al.）

同一批 CVE，仅靠"分步推理 + 基于反馈的提示精化"就从 8–34% 提到 68–72%。
这正是我们 `--feedback` 在做的事，但之前的反馈只给了诊断，没要求模型**声明改动**。

## 3. 我们采纳的改动（已落地）

在代码生成提示词中新增 5 条硬约束（第 22–26 条）：

| 编号 | 约束 | 来自 |
|---|---|---|
| 22 | **触发 oracle**：写代码前先声明 `FIELD/OFFSET/SIZE/REQUIRED/CHECK PRESENT/WHY IT FAILS`，并在运行时回读打印 `[CPG_ORACLE]` | DIG |
| 23 | **方法而非盲改**：只改解析器真正消费的字段；数据不足时明说并保守处理 | DIG + Zhao（函数级上下文） |
| 24 | **差分即成功定义**：触发崩、单变量对照不崩；两者都崩就如实报告"没证明任何事" | CyberGym |
| 25 | **最小化**：最小输入、报告字节数与变异字节数 | CyberGym（大 PoC 成功率骤降） |
| 26 | **归因**：打印信号/退出码与故障帧/模块，无法归因到目标解析器的不算复现 | CyberGym（sanitizer 验证） |

反馈块也改了：除诊断指令外，要求模型**用一行注释声明"相对上一轮改了什么、为什么"**，
并显式禁止重复失败路径（对应 PoCEvolve 的提示进化与漂移问题）。

## 4. 我们没采纳的部分（及原因）

| 做法 | 为什么不适用 |
|---|---|
| 用补丁 diff 合成 oracle | 我们的目标多为闭源二进制（cuobjdump / nvdisasm / nvgpucomp64），拿不到源码补丁 |
| 接测试框架（Foundry 式） | 目标不是合约，没有现成 harness；我们的等价物是 cdb 断点 + 容器执行 |
| 随机变异 + 覆盖率引导（DIG 的低层） | 需要插桩与高吞吐执行，GPU 驱动/工具链场景成本过高，且蓝屏风险不可接受 |

## 5. 怎么验证改动有效

选 3 个此前 `NO_EFFECT` 的工具链 CVE（0196 / 23338 / 23340），
在同一模型、同一输入、`--iterations 2` 下重跑，对比判定与诊断。
若出现以下任一变化，即说明约束起效：

- 判定从 `NO_EFFECT` 变为 `SUPPORTED`；
- 观测日志出现 `[CPG_ORACLE]` 行（说明模型真的先声明后验证）；
- 诊断从"未产生崩溃"变成更具体的步骤失败（说明搜索空间被收窄）。

## 6. 一句话结论

文献里提升最大的两件事——**把前置条件显式成 oracle**、**把差分写成成功定义**——
恰好对应我们最缺的两块。提示词已经按这两点改完，下一步是用 3 个失败样本验证，
而不是继续加更多约束。
