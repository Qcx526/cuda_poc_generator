# P5-A GPU 驱动 PoC 可行性：一天的实测与结论

报告语言：`zh-CN`。所有结论来自本机实测（GTX 1660 / Turing / Windows 10）。
实验日期 2026-10-27，驱动在两套分支上分别测试：535.98（R535）与 551.61（R550）。

## 1. 一句话结论

**入口能打开，但进不去；进不去的原因不是技术不足，而是接口在近年被系统性硬化。**

一天内做了 11 组定向实验，**11 组是否证**，0 条 PoC。但每组否证都带可复现的实验条件与判定依据，
这些否证本身构成了"为什么现代 GPU 驱动 PoC 难"的第一手证据。

## 2. 两条路线的实测结果

| 路线 | 目标 | 结果 |
|---|---|---|
| A. 内核 escape | CVE-2026-24193（越界写） | 入口可达，**在分发前被权限拒绝**（`0xC0000022`） |
| B. 用户态编译 | CVE-2024-0107（越界读，Talos 有完整报告） | 版本匹配（551.61），**未进入漏洞函数** |

## 3. 路线 A：内核 escape 的六条否证

| # | 假设 | 实验 | 结果 |
|---|---|---|---|
| 1 | NVAPI 通过 `DeviceIoControl` 访问驱动 | 在自身进程替换 nvapi64 的 IAT 槽（原指针 `0x7ffc17c958d0`，在 kernelbase 内） | 调用返回真实数据，**拦截 0 次** |
| 2 | 二进制里的 `0x1000xxxx` 是 escape 码 | 扫 nvapi64 的 31 个调用点，取 4 个码发送 | 全部 `ERROR_INVALID_FUNCTION`；类型解码为 `WAVE_OUT`/`ACPI` |
| 3 | 上述码属于 GPU 数据面 | 查出现位置 | `0x10001002` 与 `0x10000402` **成对出现在相隔约 60 字节**，是结构体版本字 |
| 4 | 设备缺命令缓冲导致硬件 escape 被拒 | 带 64 KB command buffer 重建设备 | 返回**完全一致** |
| 5 | 可从 UMD 导入项抄到真实调用 | 检查 `nvwgf2umx.dll`（100 MB） | **不导入任何 D3DKMT 函数**（走 `D3DDI_DEVICECALLBACKS` 回调表） |
| 6 | ETW 能采到真实 escape | 采样 `Microsoft-Windows-DxgKrnl`（全关键字、level 5），同时创建 D3D11 设备 | 58,165 个事件中**含 escape 的为 0**；清单 7,417 行里唯一相关事件是 Miracast 专用 |

### 3.1 已建立且可复用的能力

```
D3DKMTOpenAdapterFromHdc  → 只为取 LUID（其句柄后续全部无效）
D3DKMTOpenAdapterFromLuid → 可用句柄（实测 0x40000040）
D3DKMTCreateDevice        → 设备句柄在偏移 12（实测 0x40000080）
D3DKMTCreateContext       → 上下文句柄在偏移 32（实测 0x400000c0）
D3DKMTEscape              → Flags 在 EscapeCode 之前（偏移 8 / 12）
```

### 3.2 判别方法（可直接复用于任何 escape 目标）

同一码，`Flags=0` 与 `Flags=1` 各发一次：

| 结果 | 含义 |
|---|---|
| 两者相同 | 卡在参数校验，**与码无关**，先修结构体 |
| 两者不同 | 结构体正确，问题在权限或客户端身份 |
| 出现 `0`/`0xC00000BB` | 已到达分发，码可以开始扫 |

## 4. 路线 B：用户态编译的五条否证

目标 CVE-2024-0107（TALOS-2024-1956），确认受影响版本 **551.61 / 31.0.15.5161**，与本机一致。

| # | 尝试 | 例数 | 结果 |
|---|---|---|---|
| 1 | 合法操作数变体（`sincos-src` 语法） | 180 | 全部编译通过，0 fault |
| 2 | SM3 src 令牌字段损坏（索引/类型/重排） | 176 | 167 拒绝 / 9 通过 / **0 驱动崩溃** |
| 3 | SM2 系数令牌越界索引 | 120 | 多数拒绝 / **0 驱动崩溃** |
| 4 | opcode 字段全扫（0x00–0xFF） | 256 | **只有 `0x25` 可编译**（长度不匹配即拒） |
| 5 | 指令长度 + 截断 | 20 | 10 次 AV，**全部假阳性**（见 §5.2） |

### 4.1 已复核的代码位置（与 Talos 报告逐字节一致）

| RVA | 字节 | 含义 |
|---|---|---|
| `0x12A3560` | `48 8B 81 00 02 00 00 48 63 D2 8B 04 90` | 越界读助手 |
| `0x1503177` | `E8 E4 03 DA FF` | `call 助手` |
| `0x15030FA` | `41 8B 43 58` → `25 FF CF FF FF` → `83 F8 7D` | 分派条件 |

### 4.2 新发现：分派函数对像素着色器不进入

函数入口约 `0x15029BD`，三种输入均 `hit: false`：

| 输入 | 进入 `0x15029BD` |
|---|---|
| `ps_2_0` + 双系数 `sincos` | 否 |
| `ps_3_0` + `sincos` | 否 |
| 基线像素着色器 | 否 |

说明该函数服务于另一类输入（顶点着色器 / 纹理 / 循环路径）。

## 5. 三个"静默错误"（方法论价值最高）

共同特征：**不报错，给出一个看起来很确定的错误结论**。

### 5.1 地址与字段类

| 错误 | 表现 | 根因 |
|---|---|---|
| PE 段头字段顺序 | "该 DLL 导出 0 个符号" | `VirtualSize` 与 `VirtualAddress` 读反 |
| 导入描述符偏移 | "该 DLL 不调用任何 API" | 从描述符内部偏移读，整体错位 |
| `VS_FIXEDFILEINFO` 槽位 | 版本显示为 `1.0.65263.1213` | `FileVersionMS` 在第三个 dword |
| capstone 线性扫描 | "0 个调用点" | 遇非法字节即停，7.8 MB 只扫了开头 |
| 驱动文件选择 | 分析了 560.94 而运行的是 535.98 | 按修改时间取"最新"，DriverStore 保留全部历史 |
| 断点地址 | `0x1176D5` 永远不命中 | 该处是**对齐填充**，不是代码 |

### 5.2 判定类（最危险）

**把 d3d9 的崩溃当成了驱动的崩溃。**

截断字节码产生 10 次 `0xC0000005`，栈在：

```
d3d9!CBaseShaderValidator::DecodeNextInstruction
d3d9!CBaseShaderValidator::ValidateShader
d3d9!CD3DBase::CreatePixelShader
```

**根本没有进入 `nvgpucomp64`。** 若只看退出码，会把 10 个假阳性当成漏洞命中。

第一版归因逻辑也错过：它检查"输出里是否出现 `nvgpucomp64`"，
而模块列表里本来就有该 DLL，于是把 d3d9 的崩溃判成驱动。

**正确的判定**：

```
命中 = 退出码 0xC0000005 且 出错栈帧所属模块 == nvgpucomp64
```

### 5.3 对策

1. 任何"零结果"或"全命中"都要用**第二条独立证据**交叉验证
   （导出 0 个 → 换 kernel32 验证 1636 个；调用点 0 个 → 检查扫描覆盖率）
2. 崩溃必须**归因到模块与偏移**，不能只看退出码
3. 结构体不确定时，发**全零请求并回读哪些字节变化**，比查头文件可靠
4. 句柄有效性的判据是**能否被销毁**，不是创建返回 0

## 6. 为什么难：三个结构性原因

1. **接口分层**：文档化 API（NVAPI）→ 内部接口（回调表）→ 内核分发。每层都在收窄可达面。
2. **权限前置**：硬件 access 的 escape 在分发前被拒，非合法 UMD 客户端无法通过。
3. **观测被切断**：ETW 不记录通用 escape；UMD 无导入项可钩；只剩内联钩或全量逆向。

这三条与"没有公开 PoC"是同一件事的两面：
**不是没人研究，而是研究成果难以复现。**

## 7. 下一步：三条路线与推荐

### 路线 1（推荐）：把"可达性判定"做成产品，而不是追 PoC

**做什么**：给定一个驱动 CVE 描述 + 驱动二进制，输出三选一判定：

```
入口存在？  →  可达？  →  缺什么证据 / 在哪一步被拦
```

**为什么**：今天所有工作都是这个判定的实例。而且它与你项目的 9 个自研模块
（IR、CFG、语义匹配、可达性求解）**天然对齐**，不是旁支。

**产出**：每个 CVE 一份判定报告 + 具体证据（地址、返回码、断点结果）。
这是**可发表的形式**——负结果只要证据充分，就是结论。

**成本**：低。工具链已具备（cdb + 静态解析 + 判定规范）。

### 路线 2：换一个有公开 PoC 的目标

需要满足两个条件同时成立：公开细节 + 驱动可安装。本机（Turing）上**没有交集**。
可选支路：

- 买二手 Pascal 卡（数百元）+ R375.70 → 直接复用已建好的 D3DKMT 客户端
- 或转非显示组件（CUDA Toolkit / nvJPEG / Nsight），但偏离"驱动"主题

### 路线 3：继续逆向到 PoC

从 `vs_3_0` 试起，若仍不进入，需要**跟随调用图反查**谁调 `0x15029BD`。
属于数小时到数天的纯逆向，且不保证成功。

### 推荐组合

```
现在：路线 1（把今天的否证固化成判定能力 + 报告）
条件具备时：路线 2 的 Pascal 支路（补一条成功 PoC）
长期：路线 3 只在有明确经费/时间时才做
```
