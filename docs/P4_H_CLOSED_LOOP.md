# P4-H 全自动闭环架构与论文定位

报告语言：`zh-CN`。回答两个问题：闭环的工程形态是什么；它作为硕士论文创新点的
贡献点如何表述才站得住。

## 1. 论文贡献点的准确表述

"全自动闭环"本身不是创新——agent 循环很常见。可辩护的贡献是闭环里的三个
**约束机制**，每一个都由实测失败案例支撑：

1. **差分判定作为循环目标函数**。生成-执行循环的终止条件不是"观察到崩溃"，
   而是 `SUPPORTED`：受控样本崩溃、良性基线干净、机制对照不崩。实测依据：
   `CVE-2025-23340` 的候选让 12 个样本全崩，但 5 个对照也全崩——以崩溃为目标的
   循环会精确收敛到这种假阳性。
2. **可归因失败的结构化回流**。失败原因必须是模型能行动的具体条件（lint 罪名、
   `CUDA_ERROR_NOT_INITIALIZED`、对照全崩），"没崩"不回流。实测依据：0091 的
   35 次探测全部空转，只有归因到"未建上下文"才能驱动修正。
3. **执行分层安全门**。用户态工具链全自动；用户态驱动组件自动 + 子进程隔离；
   内核路径强制单发 + 快照前置。实测依据：0091 单点探测未蓝屏是纪律的结果，
   不是安全的证明。

表述建议：**"证据约束下的 PoC 自动合成闭环"**（evidence-constrained closed-loop
PoC synthesis）——闭环的每一步都产出可审计证据，终止条件由差分证据而非模型自述决定。

## 2. 工程形态：`src/closed_loop.py`

状态机：`generate → execute → grade → (feed back) → ...`，有界迭代。

### 2.1 配置与分层

| 层 | 执行策略 | 循环预算 |
|---|---|---|
| `userland_toolchain` | 断网容器全矩阵 | 自动多轮 |
| `driver_userland` | 宿主子进程 + 超时 | 自动，每轮限次 |
| `driver_kernel` | **默认 BLOCKED**；`allow_kernel=True` 才放行，且执行层强制单发 | 每迭代 1 次探测 |

### 2.2 停止条件（不是只有成功才停）

| 条件 | 结果 |
|---|---|
| 判定 `SUPPORTED` | 成功退出，携带理由 |
| `NOT_VERIFIED` 且**不可归因**（理由里没有模型可改的条件） | `EXHAUSTED`，提前止损 |
| `UNKNOWN` / 可归因失败 | 带原因进入下一迭代 |
| 阶段异常 | `ERROR`，记录失败阶段名 |
| 预算耗尽 | `EXHAUSTED`，携带最后一轮判定 |

"不可归因即停"很重要：循环只为可行动的失败花预算。

### 2.3 测试

`tests/test_closed_loop.py` 8 个用例：内核门、单发放行、首迭代命中、可归因
回流直到预算耗尽、不可归因提前停、阶段异常记录、grader 收到每轮状态。
全量回归 1290 passed / 66 skipped。

## 3. 还缺的三块（下一阶段）

1. **默认执行阶段**：`docker_matrix_stage` 已有骨架，还需接样本发现
   （benign/ctrl/malicious 命名 → 显式标签）与证据落盘路径；
2. **生成阶段解耦**：目前 generate 是注入点；下一步包一层子进程调用
   `main.py --package`，读取其产物路径；
3. **反馈回流通道**：把 grader 的 reasons 拼进下一轮 codegen 的 correction
   prompt——static 失败已有此通道，dynamic 失败复用同一机制即可。

## 4. 论文实验设计建议

用 23 个 CVE 的样本集做全量实验，报告三个指标：

1. **精度**：闭环判 `SUPPORTED` 的 CVE 与人工核验结论的一致率（防止假阳性率
   成为卖点）；
2. **收敛轮数**：达成 `SUPPORTED` 平均需要几个迭代（模型自修正能力的度量）；
3. **对照有效率**：差分对照实际否证了多少"看起来成功"的候选（23340 是第一个
   数据点）——这是"生成成功 ≠ 漏洞复现"论点的量化支撑。

基线对比：单次生成（无闭环）+ 人工审阅，与闭环自动判定的结果差异，
就是闭环架构的价值证明。
